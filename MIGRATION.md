# Перенос работающего бота

Переносятся три части: актуальный код, полный дамп MariaDB и весь `uploads/`. Исходники из GitHub не содержат пользователей, загруженных фраз, согласий или аудио. CSV одобренных записей не заменяет резервную копию базы.

## Подготовка нового сервера

Клонируйте репозиторий, создайте `compose.yaml`, `.env`, `config.php`, `uploads/recordings/` и `bot.log` по README. Укажите свои пароли, UID/GID и настройки VK. Соберите web, запустите db и дождитесь healthy. Рабочие события VK пока не направляйте на новый сервер.

Если там уже есть тестовая БД, сначала сохраните её отдельно. Восстанавливать рабочий дамп нужно в выделенную БД для этого бота; импорт заменяет одноимённые таблицы. Не смешивайте записи двух независимых серверов и не меняйте ID фраз/дикторов.

## Согласованная копия на исходном сервере

Договоритесь о короткой паузе с оператором панели. Остановите обработку запросов web, оставив db запущенной. Ни панель, ни CLI-импорт не должны менять базу до окончания копирования и переключения.

В каталоге исходного проекта:

```bash
(
set -eu
backup_dir="$HOME/komi-voice-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -m 700 "$backup_dir"
docker compose stop web
docker compose exec -T db sh -c 'exec mariadb-dump --single-transaction --quick --hex-blob -u"$MARIADB_USER" -p"$MARIADB_PASSWORD" "$MARIADB_DATABASE"' > "$backup_dir/database.sql"
tar -czf "$backup_dir/uploads.tar.gz" uploads
chmod 600 "$backup_dir/database.sql" "$backup_dir/uploads.tar.gz"
printf 'Копия: %s\n' "$backup_dir"
)
```

Если команда завершилась ошибкой, web остаётся остановленным. Исправьте причину либо запустите `docker compose up -d web` для отмены переноса. Если исходный сервер снова принимает записи, перед окончательным переключением нужна новая согласованная копия.

Передайте оба файла по SSH/SCP на новый сервер. Не кладите их в GitHub и общедоступные каталоги. Секреты окружения храните отдельно от исходников.

## Восстановление на новом сервере

Ниже `database.sql` и `uploads.tar.gz` — полученные файлы в каталоге проекта. Web должен быть остановлен, db — запущена. **Команда импорта предназначена для целевой БД, не для исходной рабочей.**

```bash
docker compose stop web
docker compose exec -T db sh -c 'exec mariadb -u"$MARIADB_USER" -p"$MARIADB_PASSWORD" "$MARIADB_DATABASE"' < database.sql
tar --no-same-owner -xzf uploads.tar.gz
```

Проверьте владельца `uploads`: он должен совпадать с `LOCAL_UID`/`LOCAL_GID` web. Если распаковывали обычным пользователем с этими UID/GID, `--no-same-owner` сохраняет нужного владельца. Иначе исправьте владельца перед запуском. Не применяйте `schema.sql` поверх дампа и не загружайте TXT-корпус повторно.

```bash
docker compose run --rm --no-deps web php tools/migrate.php
docker compose run --rm --no-deps web php tools/migrate-phrases.php
docker compose up -d web
```

Первая миграция меняет квоты на 1 только если отметки о её применении нет в дампе. При переносе актуальной рабочей БД отметка должна переноситься вместе с остальными таблицами.

Проверьте число фраз, участников, записей и распределение статусов на обоих серверах. Сверьте число аудиофайлов и прослушайте несколько записей через панель. Проверьте панель фраз и CSV. При незавершённых загрузках важны и таблицы `phrase_import_*`, и `uploads/phrase-imports/`.

## Переключение

1. Убедитесь, что внешний HTTPS Callback доступен и настроены правильные секрет/код подтверждения.
2. Переключите доставку событий рабочего сообщества на новый сервер. Не оставляйте два независимых обработчика одного сообщества активными: это приведёт к двум ответам и расхождению баз.
3. Проверьте `/start`, запись, повтор записи и модерацию.
4. Исходный web оставьте остановленным; резервную копию и исходную БД сохраните до проверки результата.

Если новый сервер ещё не принял новых данных, можно вернуть старый Callback и запустить исходный web. Если на новом уже появились записи или изменения, простой возврат на старую копию потеряет эти изменения: сначала остановите новые записи и согласуйте обратный перенос данных.

После восстановления уберите переданные дампы из каталога проекта в закрытое место хранения резервных копий. Нужны регулярные резервные копии как БД, так и `uploads`, с проверкой восстановления и контролем свободного места.
